# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the API with nodemon (auto-restart), reads `.env`
- `npm run start` — start the API with plain node
- `npm run migrate` — create the database (if missing) and tables (`src/scripts/migrate.js`)
- `npm run seed` — create the admin user and seed the product catalog, both idempotent/skip-if-exists (`src/scripts/seed.js`)
- `npm run jobs:auto-confirm` — one-shot job, meant for an external cron: auto-confirms receipt (moves `shipments.status` to `received`) on any shipment `delivered` for more than `AUTO_CONFIRM_DAYS` (7) with no customer confirmation (`src/scripts/autoConfirmDeliveries.js`). Idempotent, safe to run as often as you like.

Run `migrate` then `seed` before the first `dev`/`start`. There is no test suite.

Requires a `.env` file (copy from `.env.example`): `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `JWT_SECRET`, `JWT_EXPIRES_IN`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`, `CORS_ORIGIN`, `NODE_ENV`, `CUSTOMER_JWT_SECRET`, `CUSTOMER_JWT_EXPIRES_IN`, `WOMPI_BASE_URL`, `WOMPI_PUBLIC_KEY`, `WOMPI_PRIVATE_KEY`, `WOMPI_INTEGRITY_KEY`. `CORS_ORIGIN` must exactly match the frontend origin (no wildcard) — see Auth below, cookies with `credentials: true` don't work with `origin: '*'`. `NODE_ENV=production` is what flips the login cookie's `secure` flag on. `RESEND_API_KEY`/`RESEND_FROM_EMAIL` are optional — the order-confirmation email is best-effort and the server boots and checkout works without them (see Checkout/Payments below).

## Architecture

This is the API for **Stocky**, a clothing sales portal (marketplace) — sellers with their own independent shops list and sell their clothes through Stocky in exchange for a commission on each sale. It is a standalone Express + MySQL service — **fully separate from the frontend**, which lives in the sibling `../web` project (React/Vite) and only talks to this API over HTTP (`VITE_API_URL`, default `http://localhost:4000/api`). There's no shared code or monorepo tooling between the two; they're run and deployed independently.

### Request flow

`src/server.js` applies `helmet()`, `cors({ origin: CORS_ORIGIN, credentials: true })`, and `cookie-parser` before any route, then wires up seven route groups under `/api`: `authRouter`, `customerAuthRouter`, `productsRouter`, `categoriesRouter`, `colorsRouter`, `sizesRouter`, `ordersRouter`. It also owns process lifecycle: `SIGTERM`/`SIGINT` close the HTTP server and the DB pool before exiting, and `unhandledRejection`/`uncaughtException` are logged at the process level as a last-resort safety net (routes should still handle their own errors — this isn't a substitute for that).

- `authRouter` (`src/routes/auth.js`) — `POST /api/auth/login` (rate-limited: 10 requests / 15 min per IP via `express-rate-limit`) delegates credential checking to `services/authService.js`, then sets the returned JWT as an `httpOnly` cookie (`stocky_admin_token`) — **the token is never returned in the JSON response body**. `POST /api/auth/logout` clears that cookie. `GET /api/auth/me` (protected) is how the frontend checks "is there a valid session?" on load, since JS can't read an `httpOnly` cookie directly.
- `productsRouter`/`categoriesRouter`/`colorsRouter`/`sizesRouter` — public reads, `requireAuth`-gated writes (see below).

`src/middleware/auth.js` (`requireAuth`) reads the JWT from the `stocky_admin_token` cookie (`req.cookies`, populated by `cookie-parser`) — **not** an `Authorization` header — verifies it with `JWT_SECRET`, and attaches the decoded payload to `req.admin`. There is only one admin role — no permission levels. Because auth is cookie-based, any client calling this API (including the frontend's `apiFetch`) must send requests with credentials/cookies included, or `requireAuth` will always 401.

### Customer auth (separate from admin auth)

Checkout requires a customer account — a second, parallel auth system to the admin one above, not an extension of it:

- `customerAuthRouter` (`src/routes/customerAuth.js`) — `POST /api/customer-auth/register`, `POST /api/customer-auth/login` (both rate-limited, 10/15min), `POST /api/customer-auth/logout`, `GET /api/customer-auth/me` (protected). Sets/clears an `httpOnly` cookie `stocky_customer_token` — never returned in the JSON body, same as the admin cookie.
- `src/middleware/customerAuth.js` (`requireCustomerAuth`) — reads `stocky_customer_token`, verifies with `CUSTOMER_JWT_SECRET` (a **separate** secret from admin's `JWT_SECRET` — deliberately, so a bug mixing up the two cookies fails closed instead of silently cross-verifying), attaches `req.customer = { sub, email }`.
- `src/services/customerAuthService.js` — `bcrypt.hash(password, 12)`, generic "Correo o contraseña incorrectos." error whether the email doesn't exist or the password is wrong (anti-enumeration, same pattern as admin `authService.login`).

#### OTP login/register (phone or email, no password) — for the mobile app

A parallel entry path modeled on `etniapp-core`'s `UserAppAuthService`, for the React Native app (`../movil`), which can't reliably persist cookies. It never touches `register`/`login`/`getById` above — the password path keeps working unchanged for the web.

- `POST /api/customer-auth/otp/request` `{ channel: 'sms'|'email', email? , regionCode?, phone?, isLogin }` — sends the code. `isLogin` decides what's required of the account: true → account must exist (404 if not), false → account must not exist (409 if it does). Rate-limited 5/15min (stricter than password login — each call costs a real SMS or email).
- `POST /api/customer-auth/otp/login` `{ channel, email/regionCode+phone, code }` → `{ token, customer }`, and also sets the `stocky_customer_token` cookie (so the same endpoint would work for a cookie-based client too). Returning the token in the body is a deliberate, scoped exception to "the token never goes in the response body" — only these three OTP endpoints do it, because that's the only way for the mobile app to keep a session.
- `POST /api/customer-auth/otp/register` `{ channel, fullName, lastName, email, regionCode, phone, code }` → 201 `{ token, customer }`. Checks the email/phone aren't taken *before* verifying the code (so a taken identifier fails fast, leaving the code still usable), then verifies the code itself (no separate `/verify` step — a account can't be created without having proven the phone/email).
- `src/services/otpService.js` — `sendEmailCode`/`verifyEmailCode` (backed by `customer_email_otps`, `crypto.randomInt`, 10-min expiry, 5-attempt lockout — stricter than etniapp's reference, which has no attempt counter and uses a non-crypto RNG) and `sendSmsCode`/`verifySmsCode` (Twilio Verify over plain `fetch`+Basic auth, no SDK — same pattern as `paymentService.js` talking to Wompi). Missing `TWILIO_*` config throws `HttpError(503)`, not a generic 500.
- `src/middleware/customerAuth.js`'s `requireCustomerAuth` now also accepts `Authorization: Bearer <token>` when there's no cookie — cookie wins if both are present, so the web's behavior is unchanged.
- `customers.password_hash` is nullable: an OTP-only account has none, and `login()` explicitly rejects it (generic error, same as a wrong password) rather than crashing on `bcrypt.compare(password, null)`. New columns `last_name`, `region_code` (nullable — old email+password customers have neither), and `UNIQUE (region_code, phone)`.
- `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN`/`TWILIO_VERIFY_SERVICE_SID` and `OTP_EXPIRES_MINUTES`/`OTP_MAX_ATTEMPTS` are optional, same treatment as Resend — the server boots without them, only the SMS path 503s.

### Checkout / Payments (Wompi)

`POST /api/orders/checkout` (`requireCustomerAuth`, rate-limited 20/15min) is the only way an order gets created — there is no admin "create order" endpoint. `paymentMethod` is a generic `{ type, ... }` object forwarded to Wompi almost as-is — `paymentService.createTransaction` doesn't care whether `type` is `CARD`, `PSE`, `NEQUI`, `BANCOLOMBIA_TRANSFER`, or `DAVIPLATA`.

Flow (`src/services/ordersService.js` + `src/services/paymentService.js`):
1. `buildOrderFromLines` re-prices every line from the current `products` table (never trusts a client-sent subtotal/total) and pre-checks `variant_stock` for each `{color,size}` — optimistic, re-checked again in step 4.
2. The request's `amountInCents` must exactly equal the server-computed `total * 100` (COP has no minor unit, so this is an exact match, not a rounding window) — mismatch is a 409, and Wompi is never called.
3. `paymentService.chargeCard(...)` calls Wompi **before any DB write**. Wompi returns 2xx for both an **approved** and a **declined** card — the outcome travels in the response body's `status` field, not the HTTP status code — so `chargeCard` only throws on a genuine Wompi-side failure (non-2xx, network error, unparseable body); a decline is a normal, non-throwing result. The Wompi integrity `signature` is computed server-side (`SHA-256(reference+amountInCents+currency+WOMPI_INTEGRITY_KEY)`), and the request carries an `Idempotency-Key` equal to the server-generated `reference`.
4. **As long as Wompi accepted the request at all**, the order is persisted — approved, declined, or pending — matching `etniapp-core`'s actual behavior (`PersistCheckout` there never inspects the transaction status before writing). One `pool.getConnection()` transaction: re-check stock with `SELECT ... FOR UPDATE`, insert `orders` (`status` mapped from Wompi's status — `APPROVED`→`paid`, `PENDING`→`pending`, anything else (`DECLINED`/`VOIDED`/`ERROR`)→`failed`), insert `order_items`, decrement `products.variant_stock`, insert one `shipments` row (`status='pending'`), insert `payment_transactions` with Wompi's raw status. Stock is decremented and a shipment is created even on a declined card, same as the reference — a declined order still exists as a real row for back-office reconciliation; it's on `orders.status`/`payment_transactions.status`, not on the row's existence, that a caller tells approved apart from declined.
   - If this transaction fails **after** Wompi already accepted the charge (e.g. a lost stock race), `ordersService.checkout` now attempts `paymentService.voidTransaction(...)` (Wompi's void endpoint) before giving up — if the void succeeds, the client gets a 409 saying the charge was reversed automatically and to retry; if the void itself fails (normal outside same-day/pre-settlement windows), it falls back to the original behavior: logged at `fatal-payment-orphan` with the Wompi transaction id, returned as a 500 telling the client to contact support with that id for a manual refund. The auto-void path is new relative to the reference (which only logs) — untested against a real Wompi sandbox, since there are no live credentials in this environment; treat it as best-effort until verified live.
5. **Async methods (PSE/Nequi/Bancolombia/DaviPlata) land in `PENDING`** on the initial response. If Wompi didn't include a redirect URL in that response, `ordersService.checkout` polls `paymentService.getTransactionById` (up to 10×/2s, same cadence as the reference) for one before returning — the order is already persisted by this point, the polling only enriches the response with where to send the customer. The *authoritative* resolution of a pending order is the webhook below, not this poll.
6. **`POST /api/webhooks/wompi`** (public, no `requireCustomerAuth` — Wompi calls it directly) is how a `PENDING` order gets resolved to `paid`/`failed` later. `src/services/wompiWebhookService.js` verifies the event's checksum (`SHA-256(properties' values in order + timestamp + WOMPI_EVENTS_KEY)`) before trusting anything in the body — an unsigned or mis-signed POST is rejected with 401 and never touches the DB. On a valid `transaction.updated`/`transaction.created` event, `ordersService.applyPaymentUpdate` updates `payment_transactions.status` and the matching `orders.status`, and sends the confirmation email **only on the transition into `paid`** (so a repeated webhook for an already-confirmed order doesn't re-send it).
7. A real double-submit guard: the client sends its own `idempotencyKey` (generated once, e.g. when the payment form mounts); `orders` has `UNIQUE (customer_id, idempotency_key)`, and a repeated request with the same key returns the existing order without charging Wompi again — the server-generated `reference` alone does *not* protect against this, since a fresh HTTP retry would otherwise get a fresh reference.
8. After a synchronous `paid` result, `emailService.sendOrderConfirmation(...)` (Resend) runs best-effort, and **only when Wompi approved** — a deliberate deviation from the reference, which emails "confirmed" regardless of status; doing that here would mislead a customer whose card was actually declined. A send failure is logged in its own `try/catch` and never changes the 201 response or rolls back the already-persisted order. For async methods, the same email is sent instead by the webhook handler once it actually resolves to `paid` (see point 6).

`GET /api/payments/pse/banks` (public) — `paymentService.listPseBanks()` proxies Wompi's `GET /pse/financial_institutions` (using the public key, not the private one, since it's informational) and caches the result in memory for 1h; feeds the bank picker on a PSE checkout form.

`GET /api/orders` / `GET /api/orders/:id` return only the authenticated customer's own orders (404 on any order id that isn't theirs) — `listForCustomer` fetches items/shipments/payments/shipment history in 5 batched `IN (...)` queries rather than per-order, so it's O(1) roundtrips regardless of how many orders a customer has. There's no customer-facing way to change a shipment's state — only to read it.

### Línea de seguimiento del envío

`src/services/shipmentsService.js` owns the shipment status machine. `shipments.status` now has 8 values: the happy-path flow `STATUS_FLOW = ['pending','preparing','shipped','out_for_delivery','delivered','received']` (`pending` means "paid, not yet prepared" — the value the row is created with in `ordersService.checkout`; `received` is the customer's own confirmation, see below), plus two terminal exception states `cancelled`/`returned` (`TERMINAL_STATUSES`). `canTransition(from, to, actorType)` only allows moving one step forward in `STATUS_FLOW`, `cancelled` from anything before `delivered`/`received`, and `returned` from `out_for_delivery`/`delivered`/`received`; nothing is allowed to leave a terminal state. The third argument gates who can confirm receipt: `to === 'received'` is only allowed for `actorType` in `['customer','system','admin']` — a seller can never confirm their own delivery. `updateStatus(shipmentId, body, actor)` enforces this inside a `SELECT ... FOR UPDATE` transaction, stamps `delivered_at`/`received_at`/`received_source` the first time each is reached, and appends a row to `shipment_status_history` (`{ shipment_id, status, note, actor_type: 'system'|'admin'|'seller'|'customer', actor_id, created_at }`) on every change. An invalid transition is a `409`, not a `400` — the status value itself may be valid, just not reachable from the current one (or by that actor).

Three mutators:
- `PATCH /api/admin/shipments/:id` / `GET /api/admin/shipments` (`requireAuth`) — the admin can move any shipment, including confirming receipt on the customer's behalf (support cases).
- `PATCH /api/seller/shipments/:id` / `GET /api/seller/shipments` (`requireSellerAuth`) — scoped to shipments whose order has at least one `order_items.seller_id` belonging to the caller (`assertSellerOwnsShipment`, 404 if not theirs). Can advance up through `delivered`, never to `received`.
- `POST /api/orders/:id/recibido` (`requireCustomerAuth`, rate-limited 30/15min) — `ordersService.confirmReceived()`. The **only** mutation a customer can make on their own order; moves the order's shipment to `received` with `actor.type = 'customer'`. 404 if the order isn't theirs.

`ordersService.serialize()`'s `shipment` field keeps its old `status`/`trackingNumber` keys (backward compatible) and adds `carrier`, `deliveredAt`, `receivedAt`, `receivedSource`, `updatedAt`, and `history: [{ status, note, createdAt }]`. The initial history row is written in the same transaction as the `shipments` insert in `ordersService.checkout` (via `shipmentsService.appendInitialHistory`) — since a shipment row is created unconditionally at checkout regardless of payment outcome, `applyPaymentUpdate` (the webhook path) doesn't need its own insert.

### Retención de pago al vendedor, devoluciones, y pagos

The problem this section solves: before it, `sellerSalesService.js` was a pure `SUM()` over every `order_items` row on a `paid` order, forever — no record of "already paid", and a `cancelled`/`returned` shipment still counted in full.

- `RECEIPT_HOLD_DAYS = 15` / `AUTO_CONFIRM_DAYS = 7` (`src/services/reportsService.js`) — the window after `received_at` during which a return can be requested and a payout is withheld, and how long after `delivered` the system auto-confirms receipt if the customer never does (`src/scripts/autoConfirmDeliveries.js`, run via `npm run jobs:auto-confirm`, meant for an external cron — this backend has no in-process scheduler and none was added for one daily job). If the job never runs, nothing breaks in the dangerous direction: sales just stay held, never released early.
- `PAYOUT_STATE_SQL` (`reportsService.js`) — a derived (not persisted) `CASE` expression computing one of `pending | on_hold | available | paid | blocked` per `order_items` row, from `shipments.status`/`received_at`, `return_requests.status`, and whether a `seller_payout_items` row already exists. Derived on purpose: a sale moves from `on_hold` to `available` purely by the passage of time, no job required. Needs `PAYOUT_STATE_JOINS` (`LEFT JOIN shipments sh`, `return_requests rr`, `seller_payout_items spi`) in the same query.
- `sellerSalesService.listForSeller`/`summaryForAdmin` now also return a `byState` breakdown using the above — this is what fixed the `cancelled`/`returned` bug: those shipments now land in `blocked`, not counted as owed.
- `src/services/returnsService.js` — `return_requests` is `UNIQUE(order_id)`, one request per order (not per item, a product decision, not a technical limit). `createForCustomer` requires the order to be `paid`, the shipment `delivered`/`received`, and — if `received_at` is set — still within `RECEIPT_HOLD_DAYS`; outside that window it's a `409` with the policy text, not silently rejected. `resolve(id, {status, resolutionNote}, adminId)` approves/rejects; **approving does not itself move the shipment to `returned`** — authorizing a return and physically getting the item back are two different moments, the shipments endpoints already handle the latter. Sends `emailService.sendReturnResolved` best-effort (same pattern as `sendOrderConfirmation`, not the throwing OTP one).
- `src/services/payoutsService.js` — `seller_payouts`/`seller_payout_items` is the "already paid" record that didn't exist before. `create(sellerId, {orderItemIds, note}, adminId)` re-verifies every item is still `available` inside a `SELECT ... FOR UPDATE` transaction before inserting — and `seller_payout_items.order_item_id` is `UNIQUE` as the last-resort guarantee against paying the same sale twice, even under a race the application-level check missed.
- Routes: `POST /api/returns`, `GET /api/returns/me`, `POST /api/returns/:id/cancelar` (`requireCustomerAuth`) · `GET /api/admin/returns`, `PATCH /api/admin/returns/:id` (`requireAuth`) · `GET`/`POST /api/admin/seller-payouts`, `GET /api/admin/seller-payouts/disponible/:sellerId` (`requireAuth`) · `GET /api/seller/payouts` (`requireSellerAuth`, on `sellerRouter` in `sellerProducts.js`).

### Product reviews (comments left by customers)

`src/services/reviewsService.js` + `src/routes/reviews.js`, mounted at `/api/reviews`, plus one route on `productsRouter`:

- `GET /api/reviews/me` (`requireCustomerAuth`) — every review the authenticated customer has left, newest first, joined with the product's current name/image.
- `POST /api/reviews` (`requireCustomerAuth`, rate-limited 30/15min) — `{ productId, rating (1-5), body? }`. One review per `(customer, product)` — a second `POST` for the same product is a 409; use `PATCH` to edit. `product_reviews.order_id` is resolved server-side to the customer's most recent **paid** order containing that product (nullable — a review isn't required to come from a purchase made in this store).
- `PATCH /api/reviews/:id`, `DELETE /api/reviews/:id` (`requireCustomerAuth`) — 404 if the review isn't the caller's, same ownership pattern as orders.
- `GET /api/products/:id/reviews` — public, `status = 'published'` only.

`product_reviews` has no moderation UI yet (`status` exists so hiding a review later is additive, no schema change) and no admin listing — both are natural follow-ups, not implemented here.

### Service layer

Business logic (validation, queries, serialization) lives in `src/services/*.js`, one file per resource (`productsService`, `categoriesService`, `colorsService`, `sizesService`, `authService`) — routes are a thin HTTP layer that parse `req`, call a service function, and shape the response. Services never touch `req`/`res`; they take plain arguments and either return data or `throw new HttpError(status, body)` (`src/services/errors.js`). Route handlers have **no try/catch** — Express 5 forwards a rejected async handler to the global error middleware automatically, which checks `err instanceof HttpError` first (status/body used as-is) before falling through to the generic sanitized 500 (see below). When adding a new resource, follow this same shape rather than putting logic directly in the route.

### Products API and filtering

- `GET /api/products?categoria=` — public, `active = 1` only. `categoria` is interpreted in `productsService.listPublic()`: `nuevo` → `badge = 'new'`, `ofertas` → `old_price IS NOT NULL`, anything else → exact `category` match, `todo`/omitted → all.
- `GET /api/products/admin` — protected, returns the full catalog including inactive products (used by the admin dashboard table).
- `GET /api/products/:id`, `POST /api/products`, `PUT /api/products/:id`, `DELETE /api/products/:id` — standard CRUD; POST/PUT/DELETE require `requireAuth` and `productsService`'s internal `validatePayload()` (name, cat exists in `categories`, price > 0, oldPrice > price if set, img, badge in `['new','low']`, non-empty colors/sizes arrays, bestsellerOrder is a positive int if set, each `variantStock` entry has a non-negative int `stock`) — throws `HttpError(400, { errors: [...] })` on failure. The category-exists check here is a friendlier pre-check; the FK constraint (see Data model) is the actual guarantee.
- Route order matters in `products.js`: `/admin` is declared before `/:id` so it isn't swallowed by the id param route.

### Data model

Eleven tables (created by `migrate.js`, no ORM/migration framework — raw SQL, idempotent via `IF NOT EXISTS` / guarded `ALTER TABLE`):
- `admins(id, username, password_hash, created_at)`
- `products(id, name, category, description, price, old_price, image_url, badge ENUM('new','low'), colors JSON, sizes JSON, active, bestseller_order, variant_stock JSON, created_at, updated_at)`
- `categories(id, slug UNIQUE, label, sort_order, created_at)` — `products.category` has a `FOREIGN KEY ... REFERENCES categories(slug) ON DELETE RESTRICT`, so deleting a category that's in use fails atomically at the DB level (`categoriesRouter`'s DELETE route catches `ER_ROW_IS_REFERENCED_2`/errno 1451 and turns it into a 409 — there's no app-level "count then delete" check anymore, that pattern was a TOCTOU race).
- `colors(id, name UNIQUE, hex, created_at)`, `sizes(id, label UNIQUE, sort_order, created_at)` — these are the *available options* offered in the admin UI, not referenced by FK from `products`.
- `products.active` has a plain index (`idx_products_active`) since every storefront read filters on it.
- `customers(id, email UNIQUE, password_hash, full_name, phone, created_at)` — separate from `admins`, see Customer auth above.
- `orders(id, customer_id FK→customers RESTRICT, reference UNIQUE, idempotency_key, status ENUM('pending','paid','failed'), subtotal, shipping_cost, total, shipping_name/email/phone/address/city, notes, created_at, updated_at)`, with `UNIQUE (customer_id, idempotency_key)`. Money columns are plain `INT` (COP has no minor unit) — never `FLOAT`.
- `order_items(id, order_id FK→orders CASCADE, product_id FK→products RESTRICT, product_name, color, size, quantity, unit_price)` — `product_name`/`unit_price` are snapshots at purchase time, same denormalization reasoning as `products.colors`/`products.sizes` below.
- `shipments(id, order_id UNIQUE FK→orders CASCADE, status ENUM('pending','preparing','shipped','out_for_delivery','delivered','received','cancelled','returned'), tracking_number, carrier, delivered_at, received_at, received_source ENUM('customer','auto','admin') NULL, created_at, updated_at)` — one row per order (Stocky has no multi-store/service split, unlike the reference implementation this was adapted from), created at checkout regardless of payment outcome. `delivered_at`/`received_at` are set once, the first time each state is reached — see Retención de pago section for why they're denormalized instead of derived from the history table on every read.
- `shipment_status_history(id, shipment_id FK→shipments CASCADE, status, note, actor_type ENUM('system','admin','seller','customer'), actor_id, created_at)` — append-only log of every shipment status change, added by migration `0003_seguimiento_envio.js` (`'customer'` added by `0004_recibido_y_devoluciones.js`); backs the "línea de seguimiento" timeline shown to the customer. `actor_id` has no FK on purpose (it points at `admins`/`sellers`/`customers` depending on `actor_type`, and the log must never be blocked by any of those tables).
- `return_requests(id, order_id UNIQUE FK→orders CASCADE, customer_id FK→customers CASCADE, reason ENUM('no_llego','danado','no_corresponde','talla','otro'), body VARCHAR(1000) NULL, status ENUM('pending','approved','rejected','cancelled') DEFAULT 'pending', resolution_note, resolved_by, resolved_at, created_at, updated_at)` — `UNIQUE(order_id)`: one request per order, not per item. See Retención de pago section.
- `seller_payouts(id, seller_id FK→sellers RESTRICT, amount, note, paid_by, created_at)` + `seller_payout_items(id, payout_id FK→seller_payouts CASCADE, order_item_id UNIQUE FK→order_items CASCADE, gross, commission)` — the persisted record of "this seller was already paid for this sale" that didn't exist before `0004_recibido_y_devoluciones.js`. `order_item_id` being `UNIQUE` is what makes double-paying a sale impossible at the DB level, not just at the application level.
- `payment_transactions(id, order_id UNIQUE FK→orders RESTRICT, wompi_transaction_id UNIQUE, status, amount_in_cents, currency, payment_method_type, raw_response JSON, created_at)` — `status` is a raw `VARCHAR` mirroring Wompi's own status strings (not an `ENUM`), so a future webhook can update it without a migration.
- `product_reviews(id, customer_id FK→customers CASCADE, product_id FK→products RESTRICT, order_id NULL FK→orders SET NULL, rating TINYINT 1-5, body VARCHAR(1000) NULL, status ENUM('published','hidden') DEFAULT 'published', created_at, updated_at)`, `UNIQUE (customer_id, product_id)` — see Product reviews above.

`products.colors`/`products.sizes` (`[{ name, hex }]` / `[string]`) are each product's own snapshot of which options it offers, and `variant_stock` (`[{ color, size, stock }]`) is optional per-combination inventory — none of these three JSON columns have a FK back to `colors`/`sizes`; that's a deliberate denormalization (a product's color/size list is captured at edit time, not live-joined), not an oversight. `bestseller_order` (nullable int, 1-3) drives which products show in the storefront hero carousel. `services/productsService.js`'s `serialize()` is the single place that maps DB snake_case rows (`category`, `old_price`, `image_url`, `bestseller_order`, `variant_stock`) to the camelCase API shape (`cat`, `oldPrice`, `img`, `bestsellerOrder`, `variantStock`) the frontend expects — keep both in sync when changing either side.

### Seeding

`src/scripts/seed.js` is safe to re-run: it checks `admins` for the configured `ADMIN_USERNAME` and `products` for any row before inserting, so it never duplicates data. The seeded catalog (15 products) mirrors what used to be hardcoded in the frontend before it was migrated to fetch from this API. It also seeds one throwaway test customer (`cliente.prueba@stocky.test` / `prueba1234`) for exercising the checkout flow manually — note seeded products don't get a `variant_stock` value, so set one on a product before testing checkout against it (there's no stock to decrement otherwise).

### Sellers (dueños de la ropa) — a third, separate auth system

Stocky is not a shop itself — it's a sales portal (marketplace): individual owners ("sellers") run their own separate shops/businesses and list their clothes through Stocky, which keeps a commission on each sale made via the portal. This is **not** an extension of admin or customer auth — it's a third parallel system, same reasoning as customer vs admin (a bug mixing up cookies must fail closed):

- `sellers(id, email, password_hash, full_name, phone, commission_rate DECIMAL(5,2), status ENUM('pending','approved','rejected'), ...)`. A seller registers themselves via `POST /api/seller-auth/register` (public, rate-limited) and starts `pending` — no cookie is issued at registration, since there's no session to give yet. Only an admin can move `status` to `approved`/`rejected` (`PATCH /api/sellers/:id`, `requireAuth`).
- `src/services/sellerAuthService.js` / `src/middleware/sellerAuth.js` mirror `customerAuthService.js`/`customerAuth.js`: `bcrypt.hash(password, 12)`, a generic "Correo o contraseña incorrectos." on login (checked **before** the status check, so a not-yet-approved account doesn't leak that the email exists), cookie `stocky_seller_token` verified with its own `SELLER_JWT_SECRET`. `requireSellerAuth` re-reads `status` from the DB on every request — a token issued before an admin revokes approval must stop working immediately, not just at next login.
- `products.seller_id` (nullable FK → `sellers.id`, `ON DELETE RESTRICT`) is who owns a product; `NULL` means it's Stocky's own stock — an exception to the normal seller-owned model, not the rule. Today that's only the seeded catalog, but the schema deliberately leaves room for Stocky to sell its own merchandise directly in the future. `productsService.js` has two parallel sets of functions: `create`/`update`/`remove`/`listAdmin` (admin, full curation) and `createForSeller`/`updateForSeller`/`removeForSeller`/`listForSeller`/`getForSeller` (portal, scoped to `WHERE seller_id = ?`). A seller product that doesn't belong to the requesting seller returns **404, never 403** — same anti-enumeration reasoning as `getForCustomer` in orders. `validatePayload(body, { allowCuration })` gates `bestsellerOrder` and `sellerId` reassignment behind `allowCuration: true` (admin only) — a seller can't put themselves in the hero carousel or hand their product to someone else.
- **Seller products publish directly to the storefront** — there is no admin approval queue for individual listings, only for the seller *account*.
- `order_items.seller_id` / `order_items.commission_rate` are **snapshots taken at checkout**, not live joins — same denormalization reasoning as `product_name`/`unit_price`. `ordersService.buildOrderFromLines` reads the seller and their current `commission_rate` off `products`/`sellers` once, at the moment of purchase; if the commission is renegotiated later, past sales don't retroactively change. There's no FK from `order_items.seller_id` to `sellers` on purpose — a seller's sales history must never block deleting them (deletion is still blocked while they have live `products` rows, via the `products.seller_id` FK).
- `src/services/sellerSalesService.js` computes gross/commission/payout **from the `order_items` snapshot**, filtered to `orders.status = 'paid'` only (a declined order persists as a row per the checkout design above, but nobody is owed money for it). `listForSeller` backs `GET /api/seller/sales` (a seller's own numbers); `summaryForAdmin` backs `GET /api/admin/seller-sales` (one row per seller). Both take optional `from`/`to` (`YYYY-MM-DD`) query params and now also return `byState: {pending, onHold, available, paid, blocked}` — see "Retención de pago al vendedor, devoluciones, y pagos" for what actually moves a sale between those and where the real payout record lives (`seller_payouts`, not this report).
- Routes: `sellerAuthRouter` → `/api/seller-auth/*` (public register/login/logout/me), `sellerRouter` → `/api/seller/*` (`requireSellerAuth`; products + `/sales`), `sellersRouter` → `/api/sellers/*` (`requireAuth`; admin list/PATCH status+commission/DELETE — there's no admin POST, the seller creates their own account via register).

### Reportes (admin + vendedor)

`src/services/reportsService.js` is the analytics layer sitting on top of the same `order_items`/`orders` snapshot `sellerSalesService.js` uses — `PAID_ONLY`, `dateRange()`, `GROSS`, `COMMISSION` now live here and `sellerSalesService.js` imports them, so both stay consistent by construction rather than by convention. Every function takes `(range, { sellerId })`: `sellerId` present scopes to one owner's `order_items.seller_id` (the seller portal), absent means the whole store (admin).

- `summary` — KPI card: gross/commission/payout/units/orderCount/avgTicket for the range.
- `timeseries` — gross/commission/payout/units/orderCount grouped by day or month (`groupBy`, default `day`; anything else is a 400).
- `topProducts` — best-selling products by gross, `limit` (default 10, capped at 50).
- `byCategory` — same shape, grouped by `products.category` (current category, not a snapshot).
- `inventory` — one row per active product with `variantStock` (parsed same as `productsService.serialize()`) summed into `totalStock`, `outOfStock`, and `lowVariants` (any variant at or under `LOW_STOCK_THRESHOLD` = 3 units), plus `unitsSold` in the range — the point is spotting what sells and never gets restocked. The `range` here only filters `unitsSold`; stock itself is always current.

Routes: `adminReportsRouter` → `GET /api/admin/reports/{summary,timeseries,top-products,by-category,inventory}` (`requireAuth`; optional `sellerId` query param to drill into one owner). The seller portal gets the same five under `GET /api/seller/reports/*` (added to `sellerRouter` in `sellerProducts.js`) — `sellerId` there always comes from `req.seller.sub`, never from the query, same anti-cross-seller rule as the rest of the portal.
